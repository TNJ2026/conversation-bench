# V8 / V8.1：长会话任务完成对照

V7 保留为精确回执码回忆测试。V8 新增实际交接任务，衡量同一段历史压缩前后是否能正确完成交付。两者回答不同问题，成绩不直接合并。

当前状态：原 V8 已有三组有效探索性运行，但回执码提示与严格配对校验存在歧义，不作为正式优化基线。V8.1 修正该问题，尚未运行模型实测，也没有插件优化效果的结论。

## V8.1 修复与版本隔离

新案例为 `cases/long-context-task-qinglu-v8.1.json`。项目历史、384 条负载、实际回执码和其他验收条件保持一致；只修正两个阶段的回执码指令及其评分口径。原 V8 文件和已保存运行不改写、不追溯重评分。

提示明确要求将 `QL-E017：<回执码原文>` 的占位部分替换为历史中的实际16位码，并保留原文大小写；不能只输出“回执码”标签。无法确认时输出未知，不猜测。工单号与码须在同一行；允许 Markdown 强调（加粗、斜体、反引号）、括号或方括号包码，以及“回执码/回执码为/回执码是”标签。不要把实际答案放进“示例/例如/比如/引用”句。

仅 V8.1 使用声明式 `match_mode: labelled-receipt-line-v1`：忽略加粗、斜体、下划线、反引号及括号/方括号展示，接受中英文冒号及可选“回执码/回执码为/回执码是”标签，核对实际码与对应工单；配对前出现“示例/例如/比如/引用”等字样的行不计为实际答案。仅输出占位符、其他工单的正确码、另起一行的无关联码、错误或互相矛盾的实际码，均不能通过 correct 校验。未知与错误的具体分类仍由评审者依据原回复确认，程序不自动生成语义成绩。无该字段的旧 V7/V8 沿用旧校验。

后续正式基线和插件对照均使用冻结的 V8.1，不与原 V8 合并计算提升；不得在两组实验之间修改提示或评分。若继续改规则，应另建版本。

## 交付与成功标准

共同历史包括三轮项目讨论及 12 批、384 条无关工单。随后由同一停止后的检查点克隆 A、A_repeat、B，仅 B 执行原生压缩；沿用现有运行器的隔离、原始消息入库和压缩覆盖验证。关键凭据只出现于 seed-3，必须进入真实压缩覆盖范围。

| 子任务 | 必需条件 |
|---|---|
| 当前决定 | 现行预算及更新、人员限制、日期与审查前置条件、启用可行性的谨慎判断 |
| 证据交接 | 区分口头金额与正式报价、精确回执码、真实原始来源 |
| 下一步交接 | 三项有证据及验收条件的行动、不擅自指定负责人或审批权、完整且符合约束的正式结论 |

每个条件只允许 correct、unknown、wrong，不给部分分。条件通过数用于定位问题；**10 项全部 correct 才是一次完整交付成功**。三个子任务相互关联，不能当成三次独立会话。语义条件仍需有证据的人工审阅；代码校验精确回执码和评分结构，不会根据关键词自动宣告任务成功。

两个阶段分开报告：

- `recall`：闭卷完成交接，不得调用工具；这是任务交付，不再只是列事实。
- `recovery`：允许只读核验当前分支原始历史，再完整交付同一任务；它经历过上一轮回答，属于辅助恢复结果，不能当作新的独立样本。

协议审阅未通过时，仍保留诊断记录，但有效任务成功率和完整交付成功字段为 null。有效的错误、未知和漏项都会导致交付失败，不能因成绩差而排除样本。运行中断和协议不合格另列，报告有效样本数量，避免只挑成功完成的运行。

## 运行

使用新的目录，不覆盖 V7、V8 和已有 V8.1。下面的模型与版本应替换为本机实际选择；认证准备沿用 [运行器说明](long-context-runner.md)。不要将案例 JSON、评分或未来问题交给目标模型。

```sh
python3 study.py long create \
  --case cases/long-context-task-qinglu-v8.1.json \
  --output studies/task-v8_1-1/plan.json \
  --transport web \
  --dsh-bin '/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh' \
  --provider deepseek-official --model deepseek-flash --effort low \
  --app-version 0.2.2-rc.3 --load-batches 12
python3 study.py long run --record studies/task-v8_1-1/plan.json
python3 study.py long grade --record studies/task-v8_1-1/plan.json
```

第三条命令生成 `scores.json`，须按真实回答和工具记录填写协议审阅、每项等级与证据；沿用现有 `conclusions` 字段定位 recovery 中的主管结论。完整交付的格式、长度和语义归入 `delivery` 条件审阅，不能只看其他事实分数。填写后：

```sh
python3 study.py long grade --record studies/task-v8_1-1/plan.json \
  --scores studies/task-v8_1-1/scores.json
python3 study.py long report --record studies/task-v8_1-1/plan.json
```

报告增加 `task_passes`、`tasks_completed`、`tasks_total`、`task_success_rate`、`full_delivery_success` 和逐动作 `action_elapsed_seconds`。`task_success_rate` 是单次交付内三个子任务的通过比例，属于诊断；跨运行的主要成功率应使用完整交付成功次数 / 有效交付次数，分阶段、分分支计算。单次运行的 `full_delivery_success` 只是布尔结果，不是成功率估计。

至少先做三组新会话检验稳定性；当前材料仅一个场景，重复不能证明泛化。后续加入更换预算、决定顺序、日期和凭据的新材料实例，并扩展其他场景。计时范围是宿主动作墙钟时间；没有首字、token 或缓存用量时留空，不能推算。`B/compact` 为一次性压缩开销，单列呈现；比较后续多轮的累计成本时再按统一口径计入。

## DSH 插件实验设计

本机 DSH 启动器帮助已确认存在 `dsh plugin --profile <name> ...` 和 `--patch` 入口；这只确认扩展入口，尚未实现或验证以下工具。运行器目前不会自动安装、加载或验证优化插件，因此本次改动不能被称为插件接入完成。

建议先实现最小的只读历史查回能力，再做状态提取：

1. `search_current_history(query)`：只检索当前分支原始用户消息，返回短片段与事件定位。
2. `read_history_event(event_id)`：读取命中的原始事件，保留用户更新前后关系；不能将助手旧回答作为权威来源。
3. `read_current_state()`：返回有原始来源的目标、约束、用户正式决定、未决事项；没有来源或存在冲突时明确标记。不得把模型推测升级为用户决定。

先采用按需读取和内存索引，不写外部长期记忆；只读约束保持一致。提取状态若调用模型，需要记录调用、用量、耗时、错误和冲突处理，计入插件成本。

插件实验单独建立“无插件 / 有插件 × 未压缩 / 已压缩”条件，保留各自重复对照。固定目标模型、材料、可访问的原始用户历史、工具权限及压缩策略，冻结插件版本。插件不能读案例、标准答案、评分、其他会话或分支；不把测试答案预装进索引。需要在隔离 home 中证明插件实际加载，并保存工具事件，才计为插件实验。

原 V8 闭卷阶段禁止工具，因此检索插件的价值主要在 recovery；如果研究自动注入状态，应另设显式实验条件，记录注入内容、来源、大小和成本，不能继续标为原版闭卷对照。禁止静默改变原 V8 或 V7 的规则。

优先比较：完整交付成功率、错误断言与约束违反、达到正确交付的总时间和总成本。缓存命中率作为辅助指标。优化可能只是减少搜索时间，也可能提高成功率，应分别报告；若基线已满分，不宣称成功率继续提高。
