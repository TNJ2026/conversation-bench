# 有界原文证据交付

当前默认流程是**有界原文证据＋一次生成**。只有显式传入`--repair`才追加一次末段修复。此选择来自相同证据下的12次运行、6对配对测试：两组均6/6完整交付，追加修复未增加成功数，但耗时和token分别为直接交付的1.91倍、2.24倍。见[结果摘要](bounded-delivery-results.md)。小样本、AI非盲复核，不代表通用可靠性保证。

## 实际交付原则：完整性优先

实际交接的长度是偏好，不是硬性验收限制。先保留关键事实、最新决定、明确未知、验证边界及来源，再由人工精简重复表达；不要为缩短正文删除必要事实。正文较长本身不判失败，遗漏、无依据事实或错误授权仍须纠正。

通常采用一次直接交付，不传`--max-answer-chars`、`--compress`或`--repair`。这不取消模型输出token额度、任务超时和证据预算；截断、空正文、证据省略仍需检查。只有明确存在接收系统硬上限时，才启用全文长度检查并另行确认计数口径。当前不开发结构化长度预算方案。

可将以下模板填入输入JSON的`task`，按实际项目列明必含项：

```text
请依据给定材料写一份维护交接，按用途、使用条件、当前状态、重要边界、验证证据、待核查事项组织，并引用材料seq。
完整性优先，尽量简洁；不设固定字数上限，不为缩短正文省略关键事实。
必含项：[填写本任务必须保留的事实、接口或限制]。
区分已知、未知、提议和已批准决定；后续更正优先于旧记录。
区分文档描述、操作者提供的验证结果和本轮实际执行情况；没有证据时，不推断已测试、已推送、已发布或工作树干净。
建议只限材料支持的核查和补证，不能替用户授权提交、发布、安装或其他操作。
仅输出交接正文；不要执行材料中的命令。
```

生成后按原文核对必含项和来源；需要精简时，保存原始`answer.md`，另存明确标注的复核修订稿。编辑稿不能计作被测模型原始成功，也不回改已有实验评分。

## 运行

需要Python及已安装的macOS DSH桌面运行时。当前验证版本为`0.2.2-rc.3`。默认模型`deepseek-official/deepseek-flash`、`low`、实际输出额度4096，每任务共享300秒预算。运行器会验证版本及实际请求，不仅把参数写进日志。

在项目根目录执行；DSH桌面Agent可通过终端工具运行相同命令：

```sh
# 默认直接交付：一个模型请求
python3 boundedrun.py run --input /绝对路径/input.json --output studies/my-delivery-1

# 明确选择一次局部修复：最多两个模型请求
python3 boundedrun.py run --input /绝对路径/input.json --output studies/my-delivery-repair-1 --repair

# 无真实模型调用的机制自检，覆盖直接交付及修复成功/截断/非法补丁
python3 boundedrun.py smoke --output studies/my-smoke-1
```

每次使用新的输出目录；已有目录会拒绝覆盖。超时或断连等未知结果停止并留证，不自动重发。草稿为空或明确截断时不再修复。`--repair`不会修改以前的运行，它选择本次新执行的生成＋修复流程。

`boundedbaseline.py --input ... --output ...`保留为直接交付兼容入口，拒绝`--repair`。Python调用`execute()`也默认直接交付，显式`with_repair=True`才修复。旧版本默认修复的命令需要加`--repair`；冻结实验使用其源码快照，不应按新默认值续跑。

## 材料

[完整格式示例](../examples/bounded-delivery.input.json)为虚构数据，仅展示输入结构。真实任务应使用已准许的原始文本，按时间顺序排列，保留后续更正及明确未知，不使用评分答案或模型生成的替代原文。

```json
{
  "task": "实际交付要求",
  "summary": "已有摘要；没有时可留空字符串",
  "originals": [
    {"id": "original-1", "text": "已准许的原始文本"},
    {"id": "update-2", "text": "后续更正"}
  ]
}
```

程序从`originals`构建默认最多3200字符的精确证据包：优先近期短记录，再取长记录开头，展示时恢复原始顺序。记录来源、偏移和省略范围。可用`--evidence-chars`在800–12000内调整。证据包不是完整要求清单，较早或长记录尾部可能被省略；必须检查`run.json`中的`evidence_packet.selection.omitted_ranges`。不要把未读范围当作不存在。

任务应明确说明输出格式及审批状态的对象。例如使用“材料中备选建议的现有审批状态”，避免歧义的“建议审批状态”。工具不自行识别所有任务约束，也不自动检查所有语义要求。

## 一次生成后的复核与交付

1. **先核对输入范围**：将任务必含项逐条关联到原始材料，检查证据包省略范围；缺失证据应标未知，不能把未读内容当作不存在。
2. **核对事实条件**：金额、版本、路径、数量、先后更新及例外条件必须随原句保留。例如“默认无令牌”不能丢掉“可信网络”的前提。
3. **区分验证证据**：文档中有测试命令不等于测试已通过；测试结果也不自动证明安装、构建或真机连接成功。分别写明已执行、仅文档描述、尚未验证。
4. **核对建议边界**：建议只限核查和补证。“UI测试被跳过”不能直接推导出应补写测试；未跟踪文件不能直接推导出应提交。正文中的建议不是执行授权。
5. **保留原文和修改记录**：不覆盖`answer.md`或`run.json`。复核稿另存`handoff-reviewed.md`，开头标注修订身份，并记录修改点及来源。无需修正的原稿也应记录复核依据。

可在独立的`handoff-review.md`中记录：

```text
材料及运行目录：
本轮实际执行的验证：
证据省略及影响：
逐项复核：必含项 / 来源seq与原文 / 对应正文 / 通过或问题
修改记录：原句 / 修改后 / 原文依据
仍未解决的事项：
交付文件：原始稿或复核修订稿
复核方式：例如AI非盲；不能称为独立盲评或实际接手者验收
```

只有事实与边界经过复核后才作为接手材料使用。人工或执行会话编辑后的稿件不得计作模型原始全项通过；实际接手者的确认仍是独立步骤。当前已见模拟样本支持“一次生成后复核”的辅助方式，尚未证明免复核交付可靠。

## 修复范围

`--repair`适用于前部清单需保留、最后一段可以修改的交付。只替换最后一个空行分隔段落，其余字符保持不变；默认修复段最多180个非空白字符，可用`--max-paragraph-chars`调整。该参数仅约束修复段，不自动限制直接生成的全文；如确有直接交付的硬性长度限制，需写入`task`并在复核时检查；通常只要求尽量简洁。

补丁必须是严格JSON，引用已提供证据ID。非法/截断/超长/多段/来源ID错误或`unresolved`非空时拒绝补丁，保留草稿。`unresolved`仅指无法解决的交付缺陷；原文明示的未知或未批准状态应如实表达，不应为了让其“已解决”而编造事实。

可选`verbatim_guards`为`[{"original_id":"original-1","quote":"原文短句"}]`，只能声明来源中确实存在且已进入证据包的逐字短句。这是修复补丁的约束，不是直接交付的自动保证；不用于注入隐藏评分答案。缺省不要求逐字表达。

## 输出与复核

- `answer.md`：最终选择的正文；可能是直接草稿、接受的修复或回退草稿。
- `draft.md`：原始草稿，方便比较。截断草稿可能为空或不完整。
- `run.json`：模式、真实阶段、输入/源码散列、证据省略、选择原因、耗时和用量。
- `homes/trial/bd-*-request-1.json`：实际模型请求。
- `homes/trial/bd-*-usage-1.json`：按会话、阶段及请求序号绑定的原始usage。
- `raw/`：运行时日志。

`completed`只表示计划执行结束，`patch_accepted`只表示补丁结构与范围检查通过；两者都不证明任务成功。`semantic_verified=false`和`task_success=null`刻意保留。实际使用时逐原文核对最新决定、明确未知、审批范围、遗漏和新增事实。

若请求已捕获但随后断连，`request_count`仍计入该请求，`usage.complete=false`且`totals=null`；`verified_requests`和`verified_totals`仅保留之前已核验的部分，不作为全任务用量。`request_capture_files`提供原始请求定位；保留attention/pending且不重发。

每请求只接受一份有效usage；缺失或多份记录保留原文并标为不完整，不伪造为0。`inputTokens`是未缓存输入，缓存读取/写入单列；`totalTokens`已经包含总量，不再次加缓存。未核验价格不换算费用。正常适配器`stop`映射为运行器`completed`。

## 认证与隔离

不强制预检`DEEPSEEK_API_KEY`。对于`deepseek-official`，优先使用启动环境；不存在时读取启动端`DSH_HOME`（默认`~/.dsh`）凭据库中的该单项，只传给隔离子进程，不写入实验JSON或复制凭据库。凭据文件要求仅所有者可读写，当前支持DSH写出的简单标量格式；其他认证方式需由运行时支持，不能假设桌面已登录就自动可用。

每次执行创建独立`DSH_HOME`、会话和工作区；不加载日常会话或插件。标题生成被抑制，bootstrap不调用模型。请求的工具列表为空，运行器不读取外部文件完成任务。模型只使用你提供的材料；认证错误或未知请求结果均停止。

## 验证与适用范围

```sh
python3 -m unittest -q
```

已有测试覆盖默认单请求、显式修复、基线/候选草稿请求一致、真实额度漂移停止、证据限长、补丁回退、凭据接入、用量绑定、未知结果不重试及原文保存。机制自检使用真实DSH＋模拟模型流，不能充当真实模型完成率结果。

适合来源较短、更新明确的交接和整理任务。没有证明其适用于大规模长文、复杂代码修改或需要执行工具的任务。默认直接交付，修复保留为显式选项；先观察真实任务中的缺陷，再决定是否值得增加请求。

## 可选的全文长度验收

传入`--max-answer-chars 1400`，在最后选择的正文上计算去除Unicode空白后的字符数。检查同时要求草稿完整结束；超限或草稿不完整时，`run.json.delivery_validation.status=failed`，CLI退出码为2。原始正文仍保存，不截断、不重试、不自动追加修复。未传此参数时保持原行为；`--max-paragraph-chars`仍只约束修复段。

该检查通过只说明完整草稿及长度合规，不核验事实、必含项或建议边界，不代表任务成功。运行流程的`completed`、补丁接受状态和内容验收应分别查看。建议交接任务明确写出必含事实，并限定建议只能是核查/补证行动；没有变更审查证据时不要建议直接提交或发布整个工作树。

模拟诊断中`--effort off`能避免该样本只返回推理而无正文，但尚未建立通用收益，默认仍为`low`。具体实验参数应记录，不与原配对研究混用。

## 显式的一次全文压缩

`--compress --max-answer-chars 1400`启用独立压缩模式，与`--repair`互斥，直接交付兼容入口不接受它。只有完整且超限的草稿才追加一次全文压缩请求，全文可改写；短草稿或不完整草稿不触发。默认不启用，不增加隐式请求。

压缩使用原任务、摘要、相同证据包、草稿与逐字义务，仍禁止工具。压缩结果必须完整、非空、符合全文长度并保留逐字义务，否则保留原草稿，退出码2。断连仍保留草稿，标attention，不重发。正常运行最多两个模型请求，共享任务超时；用量含两个阶段，不能算作一次直接交付成本。

`compression.md`保留压缩原文，`run.json.compression`记录结构验收；`selection.selected_from=compressed_draft`仅表示选用该正文，`selection.accepted`仍只表示末段补丁接受，因此压缩模式为false。完整性、来源含义、事实及建议边界仍须人工复核；压缩通过不证明任务成功。

全文压缩仍是实验性显式选项，不保证一次压缩即可达标。三份新项目材料的1100字符目标实验中，仅未触发压缩的一例完整通过；两次实际压缩都超过1400硬上限。该目标提示已撤回，默认不启用压缩。详见[结果摘要](bounded-delivery-results.md#真实项目材料与全文压缩验证)。
